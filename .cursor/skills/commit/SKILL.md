# Commit changes

Only commit when the user explicitly asks. Never commit secrets (`.env`, credentials).

## Message format

```
<type>(<scope>): <subject>

<optional body — 1–2 short sentences>
```

### Type

| Type | Use for |
|------|---------|
| `feat` | New behavior or UI |
| `fix` | Bug fix |
| `refactor` | Restructure without behavior change |
| `chore` | Tooling, deps, config |
| `docs` | Documentation only |

### Scope (optional)

Short area name when it helps: `desktop`, `player-web`, `server`, `game-data`, `shared`, `cursor`, `design`.

Omit scope when the change spans the whole repo or scope is obvious from the subject.

### Subject

- Imperative mood: "add", "fix", "remove" — not "added" or "adds"
- Lowercase first letter
- No trailing period
- ~72 characters max
- State **what** changed, not file lists

### Body (optional)

Add only when the subject alone is unclear. One or two sentences: what was done and why if non-obvious. No bullet essays.

## Forbidden in commit messages

Never append:

- `Co-authored-by: Cursor` or any Cursor co-author line
- `Made-with: Cursor` or similar tool attribution
- `Generated by` / AI disclaimers
- Emoji or ticket placeholders unless the user supplied them

## Workflow

1. Run in parallel: `git status`, `git diff` (+ `git diff --cached` if needed), `git log --oneline -10`
2. Read recent messages and match their tone and structure
3. Stage only relevant files; never stage secrets
4. One logical change per commit — split unrelated work into separate commits when the user said "commits" or the diff is clearly mixed
5. Commit with a HEREDOC:

```bash
git commit -m "$(cat <<'EOF'
feat(desktop): add skill check modal for DM

Let the GM request rolls from players and enter d10 results against DC.
EOF
)"
```

6. Run `git status` to confirm success
7. Do not push unless the user asks

## Examples from this repo

```
feat(game-data): add combat attack, damage, and dice resolution

fix(game-data): complete bestiary weapons and combat validation

feat(desktop): add combat tracker with attack and damage flow

refactor: align vitals with rulebook and drop optional rules

feat: add DM skill check requests with player roll entry

docs(cursor): add character workflow rules for agents

chore: add Prettier with format-on-save editor config
```

## Split guidance

Prefer separate commits when changes fall into different types or layers, e.g.:

- `game-data` + `shared` protocol → one commit for core logic
- UI wiring → its own `feat(desktop)` or `feat(player-web)` commit
- Unrelated bugfix mixed with a feature → two commits

Keep coupled changes together when they do not compile or run without each other.

## If commit fails

If a hook rejects the commit, fix the issue and create a **new** commit. Do not `--amend` unless the user asked and the prior commit was yours and unpushed.

## Cursor trailer injection

Cursor may append `Co-authored-by: Cursor <cursoragent@cursor.com>` to commits made by the agent. Never leave it in the message.

After committing, verify with `git log -1 --format=%B`. If the trailer is present, strip it:

```bash
FILTER_BRANCH_SQUELCH_WARNING=1 git filter-branch -f \
  --msg-filter 'sed "/^Co-authored-by: Cursor/d"' HEAD~1..HEAD
```

To rewrite a range of commits (e.g. before push):

```bash
FILTER_BRANCH_SQUELCH_WARNING=1 git filter-branch -f \
  --msg-filter 'sed "/^Co-authored-by: Cursor/d"' <oldest-commit>^..HEAD
```

Do not use plain `git commit --amend` for stripping — the trailer is often re-injected.
